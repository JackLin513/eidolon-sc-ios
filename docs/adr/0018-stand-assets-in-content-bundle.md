# 立绘素材随内容包分发

她的立绘素材（每套衣装的三个文件、她的衣装清单）放进 `.eidolonpkg` 的 `stand/` 树，和其它内容一样出现在 `manifest.json` 的 `files` 里，逐个文件记大小和 CRC32；`content` 的计数表加一个立绘条目。角色条目多一项 `stand`：默认衣装的编号、衣装清单的包内路径。格式版本仍是 2——`content` 本来就是可扩展的「键 → 条数」表，校验不读它，所以加素材不需要升版本、老包也照样能导入。

这样立绘跟着内容包走：导入一次，设备和内容包一致；换素材只换包，不重装 App。导入仍然全有或全无，任何一个立绘文件大小或 CRC 不对，整包拒绝、保留上一份（ADR-0003 的规则不动）。

**考虑过的选项**：把素材打进 App bundle（内容包和 App 分两处更新，加一套衣装就要重装；仓库也不能存这些第三方素材）；端上从 ShinyColorsDB 现拉（要联网，依赖第三方 CDN 的可用性和路径，离线没立绘，缓存与版本都没人管）。

**代价**：内容包明显变大（每套约 1 MB，先每位角色打默认衣装加几套，全量衣装之后再说）；`content` 里多一个不成表的计数键，读的人要知道它不是数据库里的表；Mac 上同步素材仍要用上游的 `stand fetch` / `stand outfits`，导出工具只负责打包筛过的那一部分。

**没有立绘的角色**：没配偶像编号或默认衣装、或素材缺失的，包里就没有她的 `stand`，通话只显示背景——和上游没有立绘时一样，不是错误。
