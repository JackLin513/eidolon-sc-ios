# ADR-0039：每条回复的调试快照

日期：2026-11-13
状态：已接受

## 背景

排查她「为什么这样回」时，已有的回合追踪只在设置里按全局列表查看，而且受「记录回合追踪」开关和全局 retention 影响；从一条具体的回复出发，看不到该轮实际读到的世界、记忆、剧情片段和 judge 原文。调试模式需要一个直接挂在回复上的入口。

聊天回复目前不跑七表情判断；七表情只存在于通话片段（`JudgeQuestions.swift`、`SegmentEmotion.swift`），并且概率和原始响应本来就不落盘。因此本功能不新增七表情调用，也不伪造七表情数据。

## 决定

1. **入口挂在回复上。** 仅调试模式打开时，每条有快照的 assistant 回复下方出现「调试上下文」；没有快照的旧消息不显示入口。失败/取消且没有回复气泡的轮次，入口放在聊天底部的错误/重试条旁，并标为未完成。
2. **快照独立于 `turn_traces`。** 新表 `turn_debug_snapshots`（schema v24）按回复消息 id 关联；只有生成该轮时调试模式打开才写入，不要求「记录回合追踪」开启。每个对话保留最近 20 轮，自动滚动；删除对话时级联删除。调试页提供清空当前对话/全部快照。
3. **快照内容在 `performTurn` 的现有作用域采集，不新增网络调用。** 记录结构化 section（角色设定、世界、制作人、格式、此刻、日程、周期、照片、检索到的记忆/剧情）、现有 judge 的原始响应与解析结论、检索 need/query/候选/分数、每一轮实际请求（含工具轮）、模型原始输出、耗时、token usage、模型/服务，以及失败信息。正常聊天不构造快照。
4. **展示分三层。** 概览；判断模型（明确写「文本聊天不运行七表情判断；七表情只在通话片段中运行」）；检索、上下文分块、逐轮请求和原始 JSON。结构化区块默认折叠，可复制当前区块或完整调试 JSON。
5. **敏感边界。** 快照不包含 API key 或请求头；剧情/记忆原文保留，因为排查需要。调试数据只在本机 SQLite，复制/分享由用户显式触发。
6. **失败也留下部分快照。** 失败、取消、judge 失败都保留已经采集到的部分，状态标为失败/已停止；失败调试写入本身失败时静默忽略，不影响回合。

## 后果

- 调试模式会额外写一类本地数据；正常模式不写。ADR-0026 的「调试接口不写回合追踪」约束针对正常回合追踪和统计；本表的用途就是调试现场，不复用 `turn_traces` 的 retention。
- schema v24 只增加一张表和索引，旧库自动迁移；`TurnDebugSnapshot` 的 JSON 字段全部 optional 以外的向后兼容通过可选字段和旧样例测试保证。
- 七表情仍然只在通话中运行；本功能不改变通话行为，也不在聊天里新增情绪判断成本。
- 第一版只覆盖普通文本聊天；通话、朋友圈/主动搭话后续再复用同一快照类型。

## 考虑过的选项

- **直接复用 `turn_traces`**：实现最小，但依赖用户开启 tracking，且 trace 会被全局 retention 清掉，不符合「每条回复可回看」的承诺。
- **在聊天里加七表情判断**：能显示七表情，但会改变正常聊天的成本和延迟；用户明确只要调试信息，不采用。
- **消息表加 JSON 列**：查询简单，但每条消息都背调试负载，且失败轮没有消息行；改用独立表。
