# 立绘在端上用本地 WKWebView 跑 Spine 播放器

取代 ADR-0001 里「立绘不做」的结论。立绘是原作官方的 Spine 3.6 骨骼动画（每套衣装三个文件：`data.json`、`data.atlas`、`data.png`），不是生成的图片，所以端上要跑官方的 Spine 运行时。现在用一个不联网的 `WKWebView`：页面和素材都从本机取，素材经自建的 URL scheme 处理器按内容包内的相对路径提供（`file://` 下的 `fetch` 会被 CORS 挡住，自建 scheme 能带 CORS 头，也只暴露内容包目录）。页面里是上游 vendored 的 `spine-webgl` 3.6 和由上游 `StandEngine` 改编的播放器，播放器只负责播：给它「哪条轨道放哪个动画、混多久」，它照做，并把加载到的动画名与时长报给 Swift。

**立绘指令和动画表在 Swift**：情绪、嘴动不动、看不看制作人、点头摇头这四件事怎么算（上游 `standDirection`），以及某种情绪配哪些动画、找不到时的回退顺序、哪些动画不算嘴型（上游 `standAnimations`），都移植进 `EidolonCore`，离线单测，用例照上游的两份测试搬。这样和引擎有关的行为在 `swift test` 里可验，桥接层只剩搬运。

**渲染接缝**：界面层只认一个 `StandRenderer`（加载一套衣装、给一个立绘指令、暂停/继续），现在是 `WKWebView` 适配器，将来可以是 Metal + 自写的运行时。换实现只动这一个适配器。

**为什么不用 Swift 重写**：Spine 3.6 没有官方的 Swift 运行时，重写等于自己实现一套骨骼动画；而上游引擎里还压着 3.6 的一串坑（末端裁切、`loop_start`、`relay`、嘴冻在第 0 帧、预乘 alpha、context loss），照抄一遍 JS 比在 Swift 里把它们重新踩一遍便宜得多。画面是每帧重绘的热点，也不适合交给 SwiftUI。

**代价**：多一层 WebView 和一个 JS 桥（约 300 KB 运行时 + 播放器），首帧比原生绘制慢一拍，调试要靠 Safari 的 Web Inspector；`spine-webgl` 与立绘素材都有第三方版权，**都不进仓库**——运行时由 `tools/` 的脚本从上游 checkout 拷进构建产物，缺了就没有立绘（通话只剩背景），代码里保留走到原生运行时的那条路。

**考虑过的选项**：直接重写成 Swift + Metal（可控、可调试，但要把上面的坑重打一遍，且 3.6 的运行时实现要自己写）；由 Mac 端渲染成视频流（要联网和一台常开的机器，和「手机独立运行」冲突）。
