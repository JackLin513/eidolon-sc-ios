# 上游模块的移植路线

上游（`Sallyn0225/eidolon-sc`）一直在长。这份文档记两件事：**端上还差哪些大模块**，以及**先做哪个**。它回答的是「接下来做什么」，不是「怎么做」——每个模块动手时各开一张 spec。

对照的上游版本：`bebc13a8`。端上已经完成的部分见 README 的「现状与边界」。

## 怎么排序

按三条比，前一条能分开就不看后一条：

1. **每天会不会碰到**——打开 App 就能用上的（朗读、礼物、成就）优先于偶尔翻的页（日历、统计、数据包）。
2. **要不要新增外部服务**——端上现在只直连对话模型、判断模型、向量化/重排、Sonosx/Fish Audio。要多接一家（比如生图）就往后排，因为那是一家新钥匙、一套新失败方式、一份新审核。
3. **能不能复用端上已有能力**——复用越多越靠前。朗读复用通话的语音合成，礼物复用酒吧已经做的好感奖励与本地库，都是几乎不新增依赖的。

「支持」的粒度：每个模块先做**端上最小闭环**（能日常用、能写进 README 的特性列表），和上游的差异写进那张 spec 的「范围外」。不做服务端才有的东西。

## 永久不做

上游这些东西只在「一个部署服务很多人」时才有意义，端上是单人单机、没有账号：

- 登录 / OAuth、多用户、邀请与封禁
- 后台（配置、用户、公告）、**限额**与用量看板
- 多标签互斥、管理员看用量

## 记下来的两笔

- **「看板」不是整个丢掉**：它的用量与时花费部分，端上可以做成设置里的「用量与花费」一页，读本机的调用记录——上限、计费、按用户拆分这些都不搬。它作为候选里的**第 4 项**的一部分（和统计一起）。
- **照片**如果被提前（比如为了展示效果），先要定两件事：NovelAI 的钥匙放哪、只出全年龄的兜底怎么做。
