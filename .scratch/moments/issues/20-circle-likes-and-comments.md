# 20: 圈子：其他偶像的赞和评论

**What to build:** 每条动态下面陆续出现其他偶像的赞和评论。赞的人慢慢多起来；组合伙伴在评论区说一两句，各用各的口吻，后面的人可以顺着前面的接。她们只回应这条动态和彼此之间的关系，不提正文里没写的事，也不回制作人。她生日那天，来赞和评论的人明显更多。规格见 `../spec.md`：「写一条动态」里讲圈子、素材里圈子成员的那几句、规则里讲偶像评论的几条、输出格式、名单的规矩、写坏了、露出时间；还有「存储」「接口」「前端」里讲赞和评论的几处。

**Blocked by:** 14

**Status:** ready-for-agent

- [ ] **抽圈子**写成纯函数，给定输入和随机源，返回 4–6 人：
  - 同组合的权重最高；她角色资料「人物关系」里有一节写到的其次（「制作人」「其他偶像」两节不算）；偶尔一位别的组合的。
  - 今天过生日、和她同组合或有关系的那位必进。
  - 她生日那天扩到 8–10 人。
  - 权重是代码常量。
- [ ] **提示词**：靠后那条系统消息里，「最近 5 条」后面、「地点候选」前面加一节「圈子成员」。每位写：
  - id 和名字，写成「`hiori`：風野灯織」；
  - 她资料「人物关系」里关于这个人的那一节；
  - 这个人人设里「自称」「对他人的称呼」「口癖」三节。
- [ ] **规则**加上几条：
  - 偶像评论一两句，最多约 40 字，日语加字幕。
  - 只回应正文、配图里写出来的东西，以及她们之间的关系；正文里没有的事不提，也不对制作人说话。
  - 后面的评论可以顺着前面的接一句。
- [ ] **解析**：
  - `<likes>` 是 id 的列表，服务器也认 `name` 和 `short_name`。
  - `<comment from="…"><ja>…</ja><zh>…</zh></comment>` 有 0–3 条，按露出的顺序写。
- [ ] **名单的规矩**：
  - 赞 1–6 人，评论 0–3 人；她生日那天赞最多 10、评论最多 6。多写的按顺序截掉。
  - 圈子以外的人丢掉。
  - 某条评论缺日语或字幕，只丢这一条。
  - 赞的名单解析不了，当没人赞。
  - 每种降级都照 17 的写法记进运行记录。
- [ ] **露出时间**写成纯函数，由服务器随机定：
  - 赞在动态露出后 5 分钟到 3 小时之间，各抽各的。
  - 评论在 15 分钟到 6 小时之间各抽一个，排好序后按她写的先后分给各条。
  - 夜里照常露出。之后好感度、冷却怎么变，都不影响已经定好的赞和评论。
- [ ] **存储**：新表「其他偶像的赞和评论」，记所属动态、偶像、是赞还是评论、评论的日语和字幕、先后顺序、露出时间。登记进 `USER_DATA`。
- [ ] **时间线接口**：只给已经露出的偶像的赞（按露出的先后）和评论（按先后，带角色、日语、字幕）。没露出的不出现，也不透露有没有。
- [ ] **前端**：有赞或评论时，这一条下面多一块 `bg-muted` 圆角：
  - 第一行是心形加赞的人的名字；
  - 细线下面是评论，每条写「名字：日语」，下面一行字幕；
  - 都没有时这一块不出现。
  - `moments.test.ts` 测赞的一行、评论的写法。`DESIGN.md` 补上这一块。
- [ ] **测试**：
  - 抽圈子和露出时间的纯函数：用 `FakeRandom` 逐个给数，测权重、必进的生日偶像、她生日时的人数、评论按先后分时间。
  - 经过「跑一遍」：请求里有圈子成员的那三节和规则；名单的各条规矩和降级；赞和评论按时间陆续出现在时间线上，没到时间的不出现。
  - 新表登记（`test_database.py`）。
- [ ] **验收**：在本地构建版上造一条动态，推进时间，用 Playwright 看赞和评论陆续出现，宽屏和手机各看一次。
- [ ] 表结构有改动，部署前手动备份数据库。
- [ ] `sh scripts/affected-tests.sh <基点>` 通过，推送后 CI 全绿。
