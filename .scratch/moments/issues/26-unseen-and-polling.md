# 26: 没看过的动态：导航上的点和轮询

**What to build:** 有新动态露出，或者她回了他的评论，导航「朋友圈」上就出现一个小点，最多晚一分钟，在任何页面都看得到。打开朋友圈页，点就消失；在哪台设备上打开都算。其他偶像的赞和评论陆续露出时，不点亮这个点。开着朋友圈页时，新露出的动态、赞和评论不用刷新，最多晚一分钟出现。规格见 `../spec.md`：「接口」里讲时间线和「有没有新的」的两处；「前端」里讲点和轮询的两处。

**Blocked by:** 23, 24

**Status:** done

- [x] **上次打开的时刻**：用 14 建的每位用户一行里的「上次打开朋友圈页的时刻」。第一次给他排计划、建这一行的时候，记成那一刻，所以没打开过的也从那时算起。
- [x] **读时间线就算看过**：读时间线的同时，把「上次打开」记成这次读的那一刻。
- [x] **「有没有新的」接口**：只回一个布尔。有动态或她的回复，露出时间在上次打开之后、在现在之前，就是真。其他偶像的赞和评论不算。朋友圈对他关着时拒绝（409）。
- [x] 不在每条动态上记看没看过。
- [x] **前端**：
  - **点**：「朋友圈」上一个点，样子和「对话」上的一样（6px、`bg-foreground`），导航栏和 dock 都有。当前在朋友圈页时不出。读屏名字跟着变。
  - **轮询**：
    - 外壳每 60 秒的那次轮询多拉一次「有没有新的」：标签页在前台时才拉，切回前台马上拉一次，朋友圈关着时不拉。
    - 朋友圈页开着时，同一个轮询改成重读时间线；重读也算打开过。
  - 打开朋友圈页后，本地先把点清掉，下一次拉的时候以服务器为准。
  - `navShell.test.ts` 测：有新的时「朋友圈」上有点，在朋友圈页上没有。
  - `DESIGN.md` 补上这个点。
- [x] **测试**，照 `test_unseen_reach_outs.py` 的写法：
  - 新露出的动态、她的回复会让它变成真；其他偶像的赞和评论不会。
  - 读时间线就变回假；在另一个客户端读也算。
  - 没打开过的，从第一次排计划算起。
  - 关着时拒绝。
- [x] **验收**：在本地构建版上用 Playwright 看：
  - 停在设置页时调一次「跑一遍」，造出一条动态，一分钟内「朋友圈」上出现点；
  - 打开朋友圈页，点消失；
  - 停在朋友圈页时再造一条，它一分钟内出现在页面上；
  - 切到后台标签页时不拉，切回前台马上拉。
- [x] `sh scripts/affected-tests.sh <基点>` 通过，推送后 CI 全绿。

### 实现说明（票 26）

- **后端**（`moments.py`、`moments_api.py`）：
  - `_keep_plan` 第一次建 `moment_users` 行时把 `opened_at` 记成排计划那一刻；之后每天再排计划不动它（`COALESCE`），所以没打开过的始终从第一次排计划算起。
  - `Moments.timeline` 读之前先写 `opened_at = 现在`。
  - 新增 `Moments.unseen` 和 `GET /api/moments/unseen`，回 `{"unseen": bool}`。只算 30 天内、属于现存角色的动态和 `reply_ja` 不为空的回复，露出时间要在 `opened_at` 之后、现在之前。先过 `_require_on`，关着时回 409。没有 `moment_users` 行（从没排过计划、也没打开过）时回假。
- **前端**：
  - `navDots` 多一个 `moments` 输入，当前项是朋友圈时不亮。读屏名字是「朋友圈，有新动态」。
  - 外壳（`ConversationDirectory`）多了 `newMoments`、`momentsRead`、`rereadOnPoll`。60 秒的那次轮询只在朋友圈开着时做朋友圈这一份：朋友圈页登记了重读就重读时间线，否则问 `getMomentsUnseen`。载入外壳时也问一次。
  - 朋友圈页打开时先 `momentsRead()` 在本地清点，每读到一次时间线再清一次。读出去之后才读到时间线的「有没有新的」，回来了不算（`momentsReadCount`）。
  - 朋友圈关掉时，点的状态也清掉。
- **判断**：
  - 朋友圈页的重读失败时留着原样、不提示；首次读失败后，下一次重读成功会把失败提示换成时间线。
  - 重读发出去以后又在本地赞、评论过的，这次读回来的结果丢掉，等下一次读。
  - 「关着时拒绝」的测试并进了 `test_moment_switch.py` 列 409 的那个测试，没单独写。
- **审查里只报告、没改的**：
  - `timeline` 先记打开、再读。读本身出错时，这次也算打开过。反过来先读后记，会把读和记之间露出的那条算成看过，所以保留现状。
  - 票 14 以后、上线前就有的 `moment_users` 行 `opened_at` 是空的，要等下一次排计划才补上，在那之前「有没有新的」都回假。这个分支还没上线，不影响。
  - `ConversationDirectory` 又多管了一份朋友圈的状态，用来挡过期响应的计数器写法也和 `seenCount` 类似。这次没有抽出来。
- **验收**（本地构建版，后端临时开 `EIDOLON_MOMENTS=1`，开发用户 `moments-accept`，直接往库里种露出时间在 5 秒后的动态）：

  - 停在朋友圈页时再种一条，60 秒后出现在页面上。这期间没有问过「有没有新的」，只重读了时间线。
  - 回到设置页，没有点。
  - 假装切到后台，75 秒里一次都没拉。切回前台 4ms 内拉了一次，点随之出现。
