# 19: 工作那条

**What to build:** 她做完制作人排的工作后不久，发一条动态说今天的工作：一天有几项就串成一条，地名从这几项工作会去的地方里挑。工作那条发在她当天最后一项做完后 30 分钟到 2 小时之间，绝不会在她还没做完时就发。没排日程、或者部署关了日程时，照常发日常那条。规格见 `../spec.md`：「节奏：到点的跑一遍」里讲工作那条和到点的两处，「写一条动态」里讲素材和地点候选的两处。

**Blocked by:** 14, 17

**Status:** done

- [x] **排计划时定是哪一条**：
  - 她今天有排给她的工作已经做完或将要做完，就是工作那条，否则是日常那条。
  - 一项工作算哪一天，看它做完的那一刻（日程按制作人的时区算）落在东京的哪一天。
  - 日程关着（`EIDOLON_SCHEDULE`）时都是日常那条。
  - 今天有没有工作，不影响她发不发，只影响写什么、几点发。
- [x] **几点发**（加进 14 的排计划纯函数）：工作那条在她当天最后一项做完后的 30 分钟到 2 小时内。
- [x] **到点时**：她今天还有没做完的工作（排计划之后制作人又给她排了），就推到最后一项做完后的 30 分钟到 2 小时。推过东京 0 点也照发，仍算排它的那一天，也计入那一天的 N 条。
- [x] **素材**：
  - 给今天做完的全部工作，每项写名字和 `note`。
  - 现在只能取到今天做完的最后一项，要加一个取全部的办法，按东京日期划。
  - 工作那条不给资料种子。
- [x] **规则**：把今天做完的几项串成一条。
- [x] **地点候选**：只从这几项工作的 `places` 类别里挑；写了 `nearby` 的，不限类别、只挑东京都以外的地点（15 定的写法）。这几项都没写 `places`，就不给候选，这条不带地名。
- [x] **她生日那天**：照样分工作那条和日常那条来排时间、给素材，另外照 14 告诉她今天是她的生日。
- [x] **测试**：
  - 排计划的纯函数：用 `FakeRandom` 逐个给数，测最后一项做完后的时间区间、跨东京日期的工作算哪天。
  - 经过「跑一遍」，排日程照 `test_schedule_*` 的写法：
    - 做完工作的那天是工作那条；到点时还有没做完的就往后推；推过 0 点仍算那天。
    - 请求里有做完的全部工作、没有资料种子；候选只来自工作的 `places`，没写就没有候选。
    - 日程关着时是日常那条。
- [x] **验收**：在本地构建版上排一项马上就会做完的工作，推进时间、调一次「跑一遍」，看时间线上那条动态写的是工作。

## Comments

### 票 17 交接

- 挑候选是 `moment_draws.draw_places`，现在只有日常那条的用法（全部类别，按 `place_likes`、圣地加权）。工作那条要给它加一个限定类别的参数：只挑这几项工作 `places` 里的类别；写了 `nearby` 的不限类别、只挑 `place.nearby`；都没写 `places` 时直接不给候选（`PostMaterial.places` 为空，提示词会写「这次没有候选，写 none」）。
- 30 天排除、季节、时段、往年今天的场馆这几条照旧适用；`Moments._material` 里调它的地方要按计划的 `kind` 分开。

### 实现说明（票 19）

- **取当天的工作**：`schedule.done_at(week, day, slot, length, timezone)` 算一项工作做完的那一刻（最后一段结束时，制作人那里的钟点）。`Schedules.done_on(user_id, day)` 按东京日期取这位用户每位角色当天做完（或将做完）的全部工作：`DayJob(job, done_at, places)`，按做完的先后排；`places` 拿 `weekly_jobs.listed_id` 回现在的工作清单查（`weekly_jobs` 没存 `places`）。日程关着时返回空。只读，不计好感度。
- **排计划**：`moment_draws.Eligible.last_done`（当天最后一项做完的时刻）、`Planned.kind`（`Kind = "daily" | "work"`）、`AFTER_WORK = (30 分钟, 2 小时)`、`work_time(last_done, after, random)`。工作那条先排，日常那条再抽，和它们至少隔 `APART`。`moment_plans.kind` 存进库，`_due` 读回。
- **到点**：先照旧查到点那一刻的条件，再看工作那条：最后一项还没做完，就用 `work_time` 改 `due_at`（`_put_off`），到新的时间再查一遍条件。`day` 不变，推过东京 0 点仍算排它的那天。
- **素材和地点**：`PostMaterial.jobs`（每项「名字：note」），提示词在此刻后面加一节「# 今天做完的工作」，不给资料种子；`POST_RULES` 加「有『今天做完的工作』时，把这几项串成一条写」。`draw_places(..., within=)`：只挑这几类，带 `nearby` 时另外挑所有 `place.nearby`；工作那条不按 `place_likes`、圣地加权，各个一样。这几项都没写 `places` 时不抽，候选为空。
- `Moments` 多了必填的 `schedules`，`assembly` 传进去。
- **判断**：
  - 补排时窗口已过（白天才回来、工作早做完）：只剩一部分就在剩下的部分里抽；整个过了就改排日常那条。这样既不超出「做完后 30 分钟到 2 小时」，也守住「有没有工作不影响发不发」。
  - 工作那条之间、往后推的工作那条和别的计划之间不保证隔 1 小时：规格这句写在日常那条下面，窗口是定死的。
  - 制作人的时区只看资料里填的（后台拿不到设备时区，没填按上海），和朋友圈里「制作人的生日」一样。资料里没填、设备不在上海的制作人，算哪天、几点做完会和日程页差几个小时。
  - 排成工作那条以后日程被关、或者工作被删了，到点时退成日常那条的素材，时间不变。
  - 东京 0 点整做完的工作（制作人在东京、晚上那段）算次日。
- **验收**：本地库副本上给 Mano 排了周二下午的「去咖啡馆」（东京 19:00 做完），推进假时钟调「跑一遍」：计划是 `work`、东京 19:30；19:29 时间线为空；19:30 真模型发了一条「静かな喫茶店で、クラシックを聴きながら……」，地点「らんぶる」（咖啡馆类），运行记录 `success`。前端没改，没起构建版。副本、脚本已删。
- **审查后改的**：删了和纯函数重复的那条「晚段算东京次日」的跑一遍测试；纯函数测试补了东京 0 点、洛杉矶；改正「隔 1 小时」那条测试；到点先查条件再往后推；窗口已过的处理（见上）；去掉 `_jobs_on`；`Eligible.done` 改名 `last_done`；`is_done` 的说明指向 `done_at`。没改的判断题：`_material` 里按有没有工作分了几处三元表达式，可以拆成两个函数；`draw_places` 参数偏多，可以收成一个小类型。
