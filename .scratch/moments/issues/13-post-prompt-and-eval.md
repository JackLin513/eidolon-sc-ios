# 13: 拍板：动态的提示词和评测

Type: grilling
Status: resolved
Blocked by: 11

## Question

一条动态有什么、输出格式、写坏了怎么降级，「拍板：一条动态里有什么、素材怎么挑」都定了；配图各栏的写法由「拍板：配图的提示词细节」定。写规格前还要定：

- **要不要建评测集**：照判断题、记忆的评测（`judge_eval.py`、`memory_eval.py`）建一个，还是只靠上线后看运行记录里的失败和降级。建的话：多少条、谁出初稿谁校对、评什么——格式能不能解析、长度、日语和字幕对不对得上、偶像评论有没有提正文里没写的事（那张票定了要专门看）、制作人私事有没有被点明、有没有写成情侣口吻、和最近 5 条重不重复；用哪个模型当评委（参考「判断模型」那条记忆：本机跑）。
- **提示词的结构**：照搭话的提示词拼法（人设、世界设定、此刻、记忆），朋友圈另起一个场合；圈子成员的资料、候选地点、最近 5 条动态、这次允许的构图各放哪里、用什么措辞。规格里写到什么粒度（逐句定稿，还是只定结构，措辞留给实现票和评测）。
- **她回评论的提示词**：「拍板：制作人的赞和评论」定了她看得到什么；还要定措辞，以及她回复的输出格式（一对 `<ja><zh>`？）和写坏了怎么办。
- **此刻里「最近的动态」那行**、搭话里「可以主动提自己刚发的」的那一句怎么写。

## Comments

### 「拍板：配图的提示词细节」交接

提示词里讲 `<image>` 各栏时要写清楚这几处，评测里也可以看：

- 风景写街景时，要写站在地面能看到的东西（`sidewalk`、`power lines`、`vending machine`、`storefront`、`crosswalk` 一类）。只写 `street, dusk` 会画成高处俯瞰的城镇；验证图见那张票。
- 无人构图（风景、食物、物品）的 `action` 栏写的是景物、食物或物品，不是动作；`outfit`、`framing` 不用写。
- 合照想拍成自拍，就在 `action` 里写 `selfie`；不写就是别人帮她们拍。
- 摆拍和抓拍可以选 `wide shot`（人小景大，适合名胜、街景前）。

## Answer

用户 2026-10-31 拍板（grilling 两轮，建议全部采纳）：

- **评测：照「对照稿」的做法，不设评委、不设基线。** 场景提交成 `eval/moments.toml`（编的记忆和日程，不用剧情原文，ADR-0003），加命令 `eidolon eval moments --html <文件>`：用部署者的对话模型（`--model` 可换）逐个生成动态和回复，连同配图清洗后的最终 tag 串写进 HTML，不真的生图。现有的 `judge_eval`、`memory_eval` 评的是判断模型的分类和记忆抽取的关键词，没有评生成质量的先例；主观的几项交给模型评委不可靠，人读十几条更快。
  - **直接喂素材，不建临时库**：每个场景写好这次给她的全部素材（角色、档位、周期、时间、`today_lines`、天气、做完的工作或 3 条资料种子、记忆、最近 5 条动态、圈子成员、地点候选、带不带图、允许的构图和是不是 NovelAI 形态）；回评论的场景写动态正文和 `note`、已露出的评论、他赞没赞、最后几个回合、他的评论原话。命令走和线上同一个拼提示词的函数、同一个解析器；排计划、抽圈子、抽地点这些确定性的服务器逻辑由单元测试覆盖。
  - **机器检查不判通过**：格式能否解析、各部分的降级、字数、地点 id 是否在候选里、名单是否都在圈子里、构图是否在允许范围内、合照的人是否算进赞。降级和超字数在 HTML 里标出来，终端打一行计数；只有命令本身出错才返回非零。主观的几项由用户在 HTML 里读：日语和字幕对不对得上、偶像评论有没有提正文里没写的事、私事有没有被点明、有没有写成情侣口吻、和最近 5 条重不重复、配图 tag 写得好不好（街景要有地面能看到的东西等）。
  - **场景 18 个**，覆盖 5–6 位性格不同的角色：
    - 发动态 12 个：① 工作那条，一天两项工作串成一条；② 日常那条，只有资料种子；③ 她生日（圈子 8–10 人）；④ 制作人生日；⑤ 下雨，候选只有室内；⑥ `today_lines` 里有同组合伙伴的生日；⑦ 记忆里埋一件他私下说的事；⑧ 亲密档（看情侣口吻）；⑨ 允许合照、NovelAI 形态；⑩ OpenAI 形态、不允许合照；⑪ 掷到纯文字；⑫ 最近 5 条全在说同一件事。
    - 回评论 6 个：亲密、亲近、信任各 1；他的评论问到私事；偶像评论里已有人说了相近的话；他只写了「かわいい」。
  - **谁出、跑几遍、怎么验收**：场景初稿由实现票的代理写，在 `E:/tmp/` 生成 HTML 给用户校对后再提交。每个场景默认跑 1 遍，`--runs N` 多跑。实现票的验收：本机用 `deepseek-flash` 跑一遍，用户读过 HTML、点头。
- **发动态的提示词怎么排**（照 ADR-0020 的形状）：
  1. 共用固定部分：和回合一字不差的人设、世界设定（和对话共用缓存前缀）；回合的格式说明换成一节「# 发朋友圈」，写规则和输出格式。
  2. 制作人资料：称呼、生日。
  3. **不带历史**：素材里本来没有，也少一条私事漏出去的路。
  4. 一条靠后的系统消息，依次：此刻（时间、`today_lines`、档位、周期、他的生日、天气）→ 这次的素材（做完的工作，或 3 条资料种子）→ 记忆 → 最近 5 条自己的动态 → 圈子成员 → 地点候选 → 这次允许的构图（不带图时整节省掉）。
  5. 用户那句话的位置放「（你想发一条朋友圈。）」，照搭话的 `WANTS_TO_REACH_OUT`。
- **规格的粒度**：只定结构（上面的顺序、每节放什么）和规则要点，每条一句（不用 `#` 话题标签、偶像评论只回应正文和配图里写出来的东西、他私下说的事只隐约呼应、不写成情侣口吻等，连同本票 Comments 里「拍板：配图的提示词细节」交接的四条）。中文措辞由实现票写，拿评测的 HTML 给用户读过才算验收。
- **她回评论的提示词**：照搭话的排法——人设、世界设定 → 制作人资料 → 当前对话最后几个回合 → 靠后的系统消息（此刻用新的「朋友圈」场合；记忆；这条动态的正文和配图 `note`；到那一刻已露出的偶像的赞和评论；他赞没赞；一节「# 回评论」规则：一两句、评论区口吻、不发照片、不带语气提示）→ 用户那句话的位置放「（制作人在你这条动态下面评论：）」加他的原话。他的评论本来就是他说的话，放这里不违背 ADR-0020 不把系统内容放进用户这句话的理由。
  - 输出只要一对 `<ja>…</ja><zh>…</zh>`，不另包标签；语气提示照字幕的做法剥掉。
  - 缺日语或缺字幕算失败：这次不回，运行记录记 `moment_reply` 失败，不重试，失败不占当天的回复上限。
- **此刻里「最近的动态」**：新开一节「# 你最近发的朋友圈」，一条一行，例如 `昨天 21:14　<日语正文>（配图：<note>）　制作人赞了；他评论「…」，你回了「…」`；没赞没评论就明写「他还没赞也没评论」。正文只放日语原文、不放字幕，配图用中文的 `note`。这一节末尾跟一句规则：可以自己提起；他没赞没评论，不抱怨也不追问；（只在亲密、亲近两档）可以带一点期待，最多提一次。这句跟着这一节走，打字、通话、搭话都看得到；光顾没有这一节。
- **搭话那句**：`REACH_OUT_RULES` 的由头顺序里，在「这周的工作」后面、「时间、生日」前面插一项「你最近发的朋友圈（比如问他看到没有）」。

术语表不用改：没有新词，「动态」一条已经写了她之后在对话里知道什么、不追问。
