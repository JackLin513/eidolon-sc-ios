# 08: 走通一次搭话

**What to build:** 部署者在后台打开「搭话」后，和她聊过、关系在信任以上的用户，隔一段时间没往来，会在当前对话里看到她先说的一段话。这段话和回复一样有日语和字幕，在对话页里另起一组；对话列表的最后一句换成这次搭话，她那一行排上去。这一张走通整条路：节奏只做最基本的，内容只给基本的提示词，其余由 09–15 补全。规格见 `../spec.md`，尤其是「存储」「对话记录和对话列表」「节奏：到点的跑一遍」「生成一次搭话」「运行记录和看板」「后台设定」几节，以及 Further Notes 实现顺序的第 1 条。

**Blocked by:** None (can start immediately)

**Status:** done

- [x] **后台设定**：新增一项「搭话」，含总开关（默认关，`.env` 可开）和「每位用户每天最多几次」（正整数，默认 3）。写法照好感度那一项，放在配置页「限额与玩法」标签里、好感度后面，不试调。每天上限这一张只存不用，由 10 接上。
- [x] **存储**：
  - 新表「搭话」：所在对话、原文、日语、字幕、分段、记下的时间、看过没有、对应的运行记录。
  - 新表「搭话日程」：这一轮属于哪次往来、区间里的位置、挪到早上的位置、改定的到点。
  - 两张表都登记进用户数据，跟着对话删。
  - 「看过没有」这一张一律写成没看过，由 12 接上；「挪到早上的位置」和「改定的到点」先不用，由 10 接上。
- [x] **跑一遍**：新模块对外只有一个方法，「把现在到点的都跑一遍」。后端启动时起一个常驻循环，每分钟调一次，写法照服务状态的探测循环：启动时起、关闭时取消、异常只写日志。时钟和随机数都用注入的。
  - [x] 只看每位用户、每位角色的当前对话，而且最后一次往来在 7 天内。最后一次往来取两者里晚的那个：最后一个回合记下的时间、最后一次接通的通话结束的时间。送礼不算往来。
  - [x] 到点 = 最后一次往来 + 一段间隔。间隔按到点时的档位、在区间里按抽到的位置取：亲密 3–6 小时，亲近 8–16 小时，信任 20–36 小时；没有好感度的部署按信任算。区间写成代码常量。往来变了就重抽。
  - [x] 这些情形不搭话：总开关关着；对话已结束；当前对话还没有回合；最后一次往来之后已经搭过话；冷却中；档位是冷淡或疏远。不搭时这一遍跳过，下一遍再看。
- [x] **生成**：
  - 借部署者的对话模型，用文字回合那组设定和思考强度，用完归还；不经过自带密钥和限额。
  - 请求照文字回合的排法（ADR-0020），依次是：共用固定部分、制作人资料、历史（同样的分段截取）、每回合变的那条系统消息、最后一条用户那一边的旁白。
    - 每回合变的那条系统消息里：「此刻」一节中「打字还是通话」那一行换成「你们这会儿没在说话」；好感度只带档位语气那几行；再加上搭话的规矩，照规格「生成一次搭话」那一条写全。
    - 最后那条旁白：最后一个回合之后的对话事件，再加一句「（制作人这会儿没在和你说话。你想先给他发几句。）」。
  - 不调工具、不检索、不判断。
- [x] 照回复的格式解析成分段，解析不出内容就算失败。失败不重试，也不记下；往后推由 10 接上。
- [x] **对话记录接口**多一种 `type: "reach_out"` 的条目，带 id、原文（去掉演出提示）、日语、字幕、分段、时间。排法和对话事件一样：排在它之后第一个用户那一段前面；在最后一个回合之后的，排在末尾。
- [x] **列表的最后一句**可以是搭话，最新对话列表和某位角色的对话列表都一样。形状和她的消息一样，多一个 `reach_out: true`。最后一句在消息、对话事件、搭话三者里取最新的。
- [x] **运行记录**多一种「搭话」：
  - 记结果（成功或失败）、角色、服务调用、用量、快慢；「用了自带密钥」总是否。
  - 花费自动归进「扮演角色的 LLM · 部署者的 key」那一行。
  - 现有按种类计数的地方不把它当成回合或通话：回合趋势、按角色、用户页的近期用量、限额结算。
- [x] 对话标题、统计、「来过」都不受搭话影响；起标题用的文字不带搭话。
- [x] **前端**：
  - 对话记录里的搭话转成和她的回复一样的条目，带一个「是搭话」的标记，key 和消息分开。
  - 分组时搭话总是另起一组：上一条留着自己的时间，搭话重新带头像和名字。历史对话里也一样。
  - 列表最后一句是搭话时，照她的话显示，她那一行跟着排上去。
  - 后台配置页上出现「搭话」这一项。
- [x] **测试**：
  - 后端：推进假时钟后直接调「跑一遍」（照 `test_service_status.py` 的写法）；最后一次往来的时间照 `test_conversation_events.py` 直接改库里的；随机数用 `FakeRandom`。要覆盖：
    - 各档到点前不来、到点后来；上面列的每种不搭的情形；没开好感度时按信任。
    - 请求里有什么，而且没有工具；用的是部署者的模型，用户自带了 LLM 也一样。
    - 对话记录和列表的最后一句；对话标题、统计不变。
    - 运行记录和花费；后台设定的保存和校验；新表登记（`test_database.py`）。
  - 前端：`conversationLog.test.ts`；`messageLines.test.ts`（另起一组）；`conversationList.test.ts`（最后一句是搭话）。
- [x] **验收**：按 `docs/agents/local-acceptance.md`，在本地构建版上打开后台的搭话，改库里的时间，调一次「跑一遍」造出一次搭话。用 Playwright 看对话页里另起一组、列表的最后一句，宽屏和手机各看一次。
- [ ] 表结构有改动，部署前手动备份数据库。

## Comments

### 实现说明（票 08）

- **后台设定**：`Settings.reach_outs`（`.env` 的 `EIDOLON_REACH_OUTS`，默认关）；`live_config._ReachOuts`（`reach_outs` 项，字段 `enabled`、`per_day`，`per_day` 的 `.env` 值是常量 `DEFAULT_REACH_OUTS_PER_DAY = 3`，只能在后台改）；`LiveConfig.reach_outs` 给出 `ReachOutSettings`。前端配置页「限额与玩法」标签里好感度后面多一张「搭话」卡，新加了字段种类 `positive`（1 起的整数，不设上限）。`.env.example` 加了一行。
- **存储**：「搭话」表 `reach_outs` 在 `store.py`（`ja`、`zh`、`segments` 照回复一样存演出提示，`seen` 一律 0，`record_id` 是运行记录的 id，不设外键：运行记录 90 天后删）。「搭话日程」表 `reach_out_schedules` 在新模块 `reach_outs.py`（`contact_at`、`place`、`morning_place`、`due_at`）。两张表都登记进 `database.USER_DATA` 和 `CONVERSATION_DATA`。
- **跑一遍**：`reach_outs.ReachOuts.run_due()`，常驻循环 `keep_reaching_out()` 在 `Backend.start` 里起、`aclose` 里取消。读的是 `Store.current_conversations()`：每位用户每位角色的当前对话，带「有没有回合」、最后一次往来（最后一条消息的时间和接通的通话结束的时间取晚的）、最后一次搭话、是否已结束。区间是 `INTERVALS`，位置 `random(PLACES) / PLACES`，往来变了就整行重抽。
- **生成**：`ConversationEngine.reach_out(conversation, llm)`。请求和文字回合共用 `_prompt`，为此把 `_prompt` 的参数改成 `about_turn`（此刻那一节、照片那句）和 `closing`（检索到的，或搭话的规矩），文字回合发出的内容和顺序不变。「此刻」那一节的 `now_prompt` 改用 `Talking`（`typing` / `in_call` / `apart`）。最后那条旁白只带最后一个回合之后的对话事件，不带「回应礼物」那句（那句开头是「先回应制作人说的话」，搭话里不对）。用的是 `LiveConfig.lease()` 借出的 `chat_llm`（文字回合那组设定）。
- **对话记录和列表**：`Store.record` 里多了 `ReachOut`，排法和对话事件一样，同一时刻事件在前；`_last` 在消息、对话事件、搭话三者里取最新的。接口的搭话条目是 `{type: "reach_out", id, ja, zh, segments, created_at}`（去掉演出提示）；列表最后一句是 `role: "character"`、`text: null`，多一个 `reach_out: true`。
- **运行记录**：`RecordKind` 加了 `reach_out`。`ActivityLog.of_user`、`taken_since` 用 `TURNS_AND_CALLS` 只数回合和通话；看板先把搭话的记录滤掉再算回合、通话、趋势、按角色和活跃用户；`admission` 用自己的 `Admitted` 类型。花费照服务调用自动进「扮演角色的 LLM · 部署者的 key」。
- **标题**：`titles` 起标题前把搭话滤掉。

判断题：

- 规格里「原文、日语、字幕、分段」没有单独的「原文」列：她的回复也没有，原文就是存着演出提示的 `ja`、`zh`、`segments`，显示时去掉。
- 失败「不重试」：08 里还没有往后推，失败时把这一轮的 `due_at` 改定到「最后一次往来 + 7 天 + 1 分钟」，同一次往来不再试，等下一次往来重抽（不然每分钟都会再试一次）。
- 测试的时钟从真实的现在开始（`FakeClock(datetime.now(UTC))`）：`Store` 用真实时钟写时间，这样它写的搭话和测试改的最后一次往来先后才对得上。
- 本地验收没有在本地库上开搭话：本地库里有 14 段对话最后一次往来在 7 天内，开了会往 Sallyn 的对话里写搭话、花模型调用。改用本地库的副本（其余对话的往来时间推到 7 天前），用真模型造出一次搭话，宽屏和手机都看了另起一组和列表最后一句，后台卡也看了；副本、脚本和截图都已删掉。
- 审查里只报告、没改的：成功先记运行记录再写库（中途结束或删号时会记成成功，10 的「被拒绝」接上）；排除搭话的计数一处在 SQL（`TURNS_AND_CALLS`），一处在看板的 Python 过滤；引擎和 `titles` 各自滤一次搭话。
- `conversationList.test.ts` 没有加测试：`conversationList.ts` 不用改，列表最后一句是搭话时走的是她的话那条路，排序按最后一句的时间，现有测试已经覆盖，加了就是 `CODING_STANDARDS.md` 说的重复测试。
