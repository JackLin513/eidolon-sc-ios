# 08: 奖励：当天第一次玩完给抽奖和好感度

**What to build:** 每天（按进门那天的北京日期）第一次玩完的光顾给 1 次抽奖，并让她的好感度上升；当天之后的光顾什么都不给。好感度和礼物关着时照样能玩，也什么都不给。抽奖和每天发的一样受上限 7 约束，攒满了就不给。给了的话记一笔到账，导航「玩法」上的点照旧亮起来。好感度按这次每一杯的平均分加，最多 +0.5，从不降。冷却中的她照样加，到了解冻线就解除冷却。不留对话事件，不出胶囊。`GET /api/bar` 多一个 `reward_today`，`done` 的 `rewarded` 写上给了什么。见规格「玩完、光顾记录和奖励」里的「奖励」、接口一节的 `reward_today` 和 `done`，以及票 07 的答案。

**Blocked by:** 05

**Status:** ready-for-agent

- [ ] 发奖励和写光顾记录在同一个写事务里。要同时满足三条才给：这一天还没有别的玩完的记录；好感度和礼物开着（`LiveConfig.affinity_on`）；告别写完了。记录上记下这次发没发奖励。
- [ ] **抽奖**：先照常补上今天该发的，再加 1 次，最多到 `MAX_DRAWS`。加上了才往到账表记一笔，键按日期，比如 `bar:2026-10-26`；没加上就不记。成就的到账不受上限，这一条受，所以要新开一条受上限的发放路径，不改成就那条。
- [ ] **好感度**：每杯上得最好 0.5、上对 0.4、上错 0.1；没有「上得最好」这一档的单（直说饮品名、打比方、老样子，或者范围里没有她爱喝的），上对记 0.5。取平均。走做完工作那条路（`_raise` 的通用化）：冷却中加的是这个数，不是冷却中礼物的固定 +3；不受每天上限约束。常量放在好感度模块里。
- [ ] `done` 的 `rewarded`：给了抽奖时 `draws` 是 1，攒满了是 0；好感度加了时 `affinity_up` 是 true。关着，或者今天已经玩完过，`rewarded` 是 `null`。
- [ ] `GET /api/bar` 的 `reward_today`：今天还没玩完过光顾，并且好感度和礼物开着。
- [ ] 测试（先例 `test_schedule_job_done.py`、`test_gift_draws.py`、`test_affinity_cooldown.py`、`test_reset_card_grants.py`）：
  - 当天第一次玩完，抽奖 +1；好感度全上得最好 +0.5、全上错 +0.1，没有最好档的单上对记 0.5；
  - 攒满 7 次时不给、不记到账；
  - 冷却中加这个数，并在解冻线解除冷却；
  - 第二次玩完什么都不给，中途离开什么都不给；
  - 跨零点按进门那天算：前一天没玩完过的照给；
  - 好感度和礼物关着时 `rewarded` 为 null，库里没变；
  - 礼物状态里「最近一次到账」跟着酒吧的到账走；
  - 不留对话事件；
  - `reward_today` 在玩完前后的值。
- [ ] 把 GLOSSARY「光顾」「抽奖」「好感度」和实现对一遍。pyright、ruff 通过；提交前跑 affected-tests，并 grep 断言礼物状态返回的测试一起跑（比如 `"max_draws"`）。
