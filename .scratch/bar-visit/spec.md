# 光顾：角色来 VA-283 光顾，服务器定好点单和判定，模型照骨架现写台词；每天第一次玩完的光顾给抽奖和好感度

Status: ready-for-agent

术语以 `GLOSSARY.md` 为准，特别是「酒吧」一节（酒吧、光顾、来意、话题、饮品、材料、点单、上得最好、上对、上错、醉），以及「好感度」「冷却」「抽奖」「限额」「自带 LLM」「思考强度」「运行记录」「看板」「数据包」「玩法」「日程」「部署者」「管理者」。说酒吧、光顾、饮品、材料、点单、角色、制作人；不说小游戏、一局、来访、订单、鸡尾酒、答对。所有决定的来历在 `.scratch/bar/map.md` 和它的票里：饮品数据是票 01（调研分支 `research/bar-drinks` 的 `drinks.csv`），原版点单是票 02，口味表是票 04，点单的说法和算对的范围是票 05，一次光顾的骨架、来意和话题是票 06，判定、醉和好感度是票 07，模型怎么写、状态和出错是票 09，切块、开关、看板、数据和文档是票 10。

这是两份规格里的第一份，从当时的 main 开 `feat/bar-visit`。第一个提交从计划分支 `feat/bar` 取来这份规格、`.scratch/bar/`（地图和 13 张票）、词汇表的改动、ADR-0031 和 ADR-0003 的 2026-10-26 修订。第二份是「酒吧的店面」（`.scratch/bar-room/spec.md`），等这一份合进 main 以后再从 main 开分支，接这一份的接口；两份都合进 main 以后一起部署，不单独上线只有后端的版本。这一份**不碰正式画面**：没有玩法页的卡、没有 `/play/bar`，靠接口测试验收，另写一个开发用的终端脚本，用线上的对话模型走一遍看措辞。

## Problem Statement

- 玩法里只有抽奖、送礼、排日程，都是在页面上点几下；没有一样东西是「和她待一会儿、为她做点什么」的。issue #149 想要小游戏，而每日任务下线以后，也少了一条每天多拿抽奖次数的路。
- 制作人在原作里最常做的事是照顾她，可这里制作人没有为她亲手做什么的机会，也没有「摸清她喜欢什么」的乐趣：礼物是抽来的，她喜欢的礼物写在表里，界面上看不出来，也没法从她的话里慢慢摸清。
- 想做一个致敬《VA-11 HALL-A》的酒吧：她来店里坐一会儿，点一杯，制作人照她的话调出来。难的是每次都得不一样，又不能让模型完全自由发挥：点单要可判对错，判定不能交给模型；她说的话不能透露答案，也不能和判定对不上；花费、限额、出错都得和文字回合一样管得住。
- 酒吧是 IF：大家都到了能喝酒的年纪，她却还是她。酒吧里的事不能漏进对话和记忆，除了好感度；酒吧也得有自己的记性，她下次来时记得上次喝了什么、醉没醉。

## Solution

- **饮品和材料**：照搬原版 28 款饮品（24 款调制、4 款瓶装，不收隐藏的 Flaming Moai），五种材料、加冰、陈化、mix 和 blend、大杯份数翻倍、7 款可选 Karmotrine。仓库里一份饮品目录，配方精确匹配；对不上任何配方的是调坏的，不能上。目录通过接口交给前端。
- **每位角色的口味**：`characters.toml` 每人加五样：喜欢的口味、种类、爱喝的 1–3 款、讨厌的口味、酒量（弱、中、强）。界面上哪里都不显示。
- **一次光顾**：进门时服务器定好角色、来意、话题和点几杯（1/2/3 杯，20/60/20%）。当天（北京时间）第一次的角色按「用户加日期」定好，玩完之前重进还是她；之后随机，29 位都在池子里，冷却中的她也照样来。骨架是：进门，点单，上酒后的反应，闲聊，循环到点完，最后告别。
- **点单**：每一单先按她的口味抽一款目标饮品（爱喝的 45%、合口味的 35%、心血来潮 20%），再抽一种说法（直说名字 40%、名字加大杯 7%、口味 12%、种类 12%、几个条件叠加 8%、打比方 8%、「来杯我喜欢的」4%、「你拿主意」4%、「老样子」5%）。服务器从目标推出算对的范围和「上得最好」的几款，模型只照点单卡说出来；服务器检查她有没有说漏名字，点单备忘也由服务器套模板写。
- **判定和醉**：每杯判成上得最好、上对或上错。上错时服务器另外告诉模型错在哪；上错了也照常往下聊，不让重做，没有惩罚。醉意按上过的 Karmotrine 份数累计，到她酒量的门槛（8/14/20）就醉：这杯的反应照常写，后面换成醉的写法，不再点单，早早告别。界面不显示醉意。
- **模型写戏**：按上酒切，一次光顾调用「杯数 + 1」次，流式输出，每写完一句推一句。酒吧有自己的提示词前缀，打两处缓存标记；沿用 `<ja><zh>` 的标签格式，加上说话人和情绪。她的台词照 ADR-0001 是日语加中文字幕，制作人只有中文，每段最多一两句。每上一杯那句「请慢用」由服务器从写死的几句里挑。
- **状态和出错**：进行中的光顾放在后端内存里，每位用户同时只有一次。刷新、离开、30 分钟不动、后端重启，这次光顾就没了，不能接着。每次调用自动重试一次，还不行就让玩家「再试一次」；告别那次写不出来时用写死的句子顶上，也算玩完。
- **奖励**：服务器发出告别的那一刻算玩完。当天（按进门那天）第一次玩完的光顾给抽奖 1 次（和每天发的一样受上限 7 约束），好感度按每杯平均（上得最好 0.5、上对 0.4、上错 0.1，没有「上得最好」这一档的单上对记 0.5）上升，最多 +0.5，不降。好感度和礼物关着时照样能玩，什么都不给。之后的光顾什么都不给。
- **花费和限额**：跟文字回合一样走对话模型，自带 LLM 的用他们自己的，思考强度跟「对话模型 · 文字回合」那一项。限额加「光顾」一种，每小时默认 5 次，管理者可以给单个用户另设；用了自带 LLM 的不计数，只记下来。
- **记录**：玩完那一刻往库里写一行结果（角色、时间、来意、话题、每单的饮品和档位、醉没醉），不存台词。她下次来时记得来过几次、上次多久以前、上次每单点了什么和上没上对、醉没醉。光顾不进对话记录、不变成记忆、不留对话事件，对话里的她不知道。运行记录加一种「光顾」，看板「用量」加「酒吧」一小节。光顾记录不进数据包，删账号一起删。
- **开关**：`EIDOLON_BAR`，默认开，后台「限额与玩法」加「酒吧」卡。

## User Stories

### 进门和来的是谁

1. 作为用户，我想每次进酒吧都有一位角色来光顾，这样每次打开都有人可以招待。
2. 作为用户，我想当天第一次来的角色是定好的，玩完之前不管退出重进多少次都是她，这样不能靠反复重进挑人。
3. 作为用户，我想当天第一次的角色按北京时间的日期换，平均一个月左右轮到同一位一次，这样每天有一位新的「今天的客人」。
4. 作为用户，我想当天玩完第一次以后，再营业来的是随机的一位，这样之后可以随便玩。
5. 作为用户，我想 29 位角色都可能来，包括はづき，也包括我在对话列表里隐藏了的，这样谁都有机会来店里。
6. 作为用户，我想在冷却中的她也照样会来，态度照冷淡那一档，这样酒吧不会因为吵过架就少一个人；玩完照常给好感度，这也是哄她的一条路。
7. 作为用户，我想同时只有一次光顾在进行，另一个标签页开了新的光顾，旧的就作废，这样状态不会乱。
8. 作为用户，我想零点前进门、零点后告别的光顾按进门那天算，那天还没玩完过的话照常给奖励，这样跨零点不吃亏。

### 她为什么来、聊什么

9. 作为用户，我想她每次来都带着一个来意（收工顺路、被人惹恼了、有好事想说、睡不着……），进门时的心情跟着来意走，这样每次的戏不一样。
10. 作为用户，我想我今天排给她、已经做完的那项工作有一半机会成为她的来意，这样日程和酒吧接得上。
11. 作为用户，我想闲聊有一个话题（组合伙伴、最近的工作、过去的事、关于制作人……），由她的人设和资料去填，这样聊的内容像她。
12. 作为用户，我想同一位最近 3 次光顾用过的来意和话题不再出现，这样不会连着几次都一个理由。
13. 作为用户，我想当天是她的生日、别人的生日、日本节假日或往年今天的演出时，她进门会提一句，这样酒吧和日子对得上。
14. 作为用户，我想她对制作人的态度跟着好感度档位走，好感度关着时按正常值，这样酒吧里的她和对话里的是同一个人。
15. 作为用户，我想她在 IF 里仍是 283 的偶像、我仍是她的制作人，下班后在 VA-283 当酒保，她来就是来找我，这样不需要另一套设定。
16. 作为用户，我想她可以聊组合伙伴、事务所、她的过去，这样她不是一个陌生的客人。
17. 作为用户，我想酒吧里的她不提具体年龄、不讨论「其实没成年」，醉了也只是话多、犯困、情绪起伏、说心里话，不往暧昧和色情走，这样 IF 不越界。
18. 作为用户，我想酒吧里的她不知道我们在对话里聊过什么，对话里的她也不知道酒吧里发生了什么，这样两边互不打扰。

### 她记得上次

19. 作为用户，我想她记得自己来过几次（第一次来、来过几次、常客），打招呼的方式跟着变，这样常来有常来的样子。
20. 作为用户，我想很久没来的她会提一句好久不见，这样她记得时间。
21. 作为用户，我想她记得上次每一单点了什么、我上对了没有，可以提起来，这样上得好不好有回响。
22. 作为用户，我想她记得上次喝醉过，可能提一句「上次喝多了」，但不会因此只点无酒精的，这样醉有后话但不惩罚。
23. 作为用户，我想她不记得上次聊过什么，服务器也不存台词，这样酒吧的记性很轻。
24. 作为用户，我想中途离开的光顾不算进「她记得上次」，这样她记得的都是完整的一次。

### 点单

25. 作为用户，我想她点的饮品多半是她爱喝的或合她口味的，偶尔心血来潮，这样上了几次之后能摸清她的口味。
26. 作为用户，我想她永远不会点她讨厌的口味，这样她的讨厌是一致的。
27. 作为用户，我想同一次光顾里她不点重复的饮品，每次光顾的第一单避开她上一次光顾点过的，这样不会总是那一款。
28. 作为用户，我想她点单的说法有很多种：直说名字、名字加大杯、只说口味、只说种类（可以绕着说，「烈的」就是 Manly）、几个条件叠加、照饮品的描述打比方、「来杯我喜欢的」、「你拿主意」、「老样子」，这样每一单都要动脑子。
29. 作为用户，我想只说口味或种类时，这个口味或种类的都算对，范围里她爱喝的那几款算上得最好，这样宽的说法也有更好的答案。
30. 作为用户，我想「来杯我喜欢的」时，她爱喝的或合她心意的都算对，爱喝的算上得最好，这样摸清她口味的人有回报。
31. 作为用户，我想「你拿主意」时除了她讨厌的都算对，她爱喝的算上得最好，这样我能凭了解给她惊喜。
32. 作为用户，我想「老样子」时上次她点过的任一款都算对，备忘只写「她要上次那款」，不替我复述，这样考的是我记不记得。
33. 作为用户，我想「老样子」只在她和我至少玩完过一次光顾以后才出，「来杯我喜欢的」也一样，这样第一次来的她不会说这种话。
34. 作为用户，我想我头 3 次玩完的光顾里不出「打比方」和「几个条件叠加」这两种最难的，这样新手先熟悉调酒。
35. 作为用户，我想她没提到的条件不管：没说无酒精，含不含酒都行；没说大杯，做大杯也算对，这样不会被没说出口的条件判错。
36. 作为用户，我想酒量弱的她点能选含不含酒的饮品时，常补一句「不要酒精」，这样酒量也体现在点单里。
37. 作为用户，我想她说了不要酒精却上了含酒的算上错，这样她说的话有分量。
38. 作为用户，我想不该说名字的说法里她真的不说出任何饮品的名字，该说名字的真的说出来，这样点单不会白送答案，也不会说偏。
39. 作为用户，我想她的日语台词里饮品名用日文版的译名（シュガーラッシュ），中文字幕和备忘用英文原名（跟官方中文版一致），这样和原版对得上。
40. 作为用户，我想每一单都有一句点单备忘，用制作人的口吻复述她要什么（「她要 Sugar Rush，大杯。」「她要甜的，不要酒精。」；打比方的复述她那句字幕），即使模型说偏了备忘也是准的，这样我可以对着备忘调。
41. 作为用户，我想不做「再问一次」，也没有提示，这样和原版一样只靠听。

### 调酒和上酒

42. 作为用户，我想调法照原版：五种材料按份数加、总共不超过 20 份，加冰、陈化两个开关，摇不到 5 秒是 mix、摇满 5 秒是 blend，这样玩过原版的人上手就会。
43. 作为用户，我想份数、冰、陈化、调法都和某个配方完全一致才是那一款，大杯是份数全部翻倍，这样调法有讲究。
44. 作为用户，我想能选 Karmotrine 的饮品加多少都还是那一款，加 0 份就是无酒精的，这样可以照她的要求调。
45. 作为用户，我想对不上任何配方的调坏了，不能上，只能倒掉重调，次数不限，这样调坏不算上错。
46. 作为用户，我想恰好调成另一款的就是那一款，可以上，照常判，这样调错了配方也只是上错。
47. 作为用户，我想照 Flaming Moai 的配方调出来也算调坏的，这样隐藏款不会凭空出现。
48. 作为用户，我想 4 款瓶装（Absinthe、Rum、Mulan Tea、A Fedora）一直都在，直接就能上，这样配方书的「瓶装」一栏有用。
49. 作为用户，我想每上一杯时制作人说一句「请慢用」一类的话，这样上酒有个仪式。

### 上了之后

50. 作为用户，我想每杯的结果是三档之一：上得最好、上对、上错，她的反应跟着档位变，这样上得好有回报。
51. 作为用户，我想上错时她的反应知道错在哪（口味对了种类不对、她讨厌的口味、说了不要酒却有酒、完全不对、不是上次那款），这样我能从反应里学到她的口味。
52. 作为用户，我想上了她讨厌的口味、或者说了不要酒却有酒时，她明显地不喜欢，这样这两种错有分量；但好感度和别的上错一样，这样不过分惩罚。
53. 作为用户，我想上错了她抱怨几句就照常往下聊，下一单照点，不让重做也不赶人，这样一次错不会毁了整次光顾。
54. 作为用户，我想调法和判定只由服务器判，模型照判定写反应，这样她的反应不会和结果对不上。

### 醉

55. 作为用户，我想她喝下的 Karmotrine 一杯杯累计（大杯按翻倍后的份数），到了她酒量的门槛就醉了，这样酒精有后果。
56. 作为用户，我想酒量弱的两杯 Beer 就醉、中等的要三四杯、强的除非故意灌很难醉，这样酒量有差别。
57. 作为用户，我想瓶装也算份数（Absinthe 6、Rum 6、A Fedora 3、Mulan Tea 0），Mulan Tea 算无酒精，这样瓶装和调制的一个尺子。
58. 作为用户，我想她醉的那一杯的反应照常写，之后话多、犯困、情绪起伏、说心里话，不再点单，聊几句就醉着告别，这样醉了的戏有完整的收尾。
59. 作为用户，我想把她灌醉不算上错，也不加分减分，没有「灌醉才听得到」的隐藏分支，这样不鼓励也不惩罚。
60. 作为用户，我想界面上不显示她醉到哪了，这样只能从她的样子看出来。

### 她和制作人的台词

61. 作为用户，我想她的台词是日语加中文字幕，制作人的台词只有中文，这样和对话、通话一致（ADR-0001）。
62. 作为用户，我想制作人也有台词，但每段最多一两句，基本是接话，这样制作人是酒保而不是主角。
63. 作为用户，我想每句她的台词带一个情绪，立绘照着换动作，这样她的表情跟着话走。
64. 作为用户，我想台词一句一句地出来，反应那几句先到，不用等整段写完，这样上了酒很快就有回应。
65. 作为用户，我想吧台上没有选项，我能影响这次光顾的只有上什么酒，这样和原版一样。
66. 作为用户，我想她告别时用一句话带出这次喝得怎么样，可以说下次再来，这样结尾有回顾。

### 玩完和奖励

67. 作为用户，我想她告别的那一刻这次光顾就算玩完了，醉了提早告别也算，这样玩完的标准清楚。
68. 作为用户，我想当天第一次玩完的光顾给 1 次抽奖，和每天发的一样攒到 7 次为止，攒满了就不给，这样酒吧不会让抽奖次数膨胀。
69. 作为用户，我想当天第一次玩完的光顾让她的好感度上升，上了她想要的升得多、上错了升得少，最多和做完一项工作一样多，从不降，这样认真调有回报，调错也不倒扣。
70. 作为用户，我想当天之后的光顾什么都不给，这样每天一次的奖励不能刷。
71. 作为用户，我想光顾结束时只告诉我得到了什么（抽奖 +1、好感度上升的方向），不显示数字、不给评分，这样结束是轻的。
72. 作为用户，我想酒吧给了抽奖次数时，导航「玩法」上的点照常亮，这样我知道有新到的抽奖次数。
73. 作为用户，我想好感度和礼物关着时照样能玩，只是什么都不给，这样酒吧不依赖判断模型。
74. 作为用户，我想跟上得好坏无关，只要玩完就给抽奖，这样不会调酒的人也拿得到。

### 中途离开和出错

75. 作为用户，我想中途离开、刷新、关掉页面、30 分钟没动作以后，这次光顾就没了，下次从店门口重新开始，什么都不给，这样状态简单。
76. 作为用户，我想中途离开后重新开始，当天第一次的角色仍是她；当天已经玩完过的，重新开始会随机换人，这样规则一致。
77. 作为用户，我想模型偶尔出错时自动重试一次，我察觉不到，这样一次抖动不打断。
78. 作为用户，我想重试也失败时看到一句短的出错提示和「再试一次」，停在这次调用之前，这样我能接着玩。
79. 作为用户，我想告别那次实在写不出来时，用写死的句子顶上，照样算玩完、照样给奖励，这样最后一步不会因为服务出错白玩。
80. 作为用户，我想她点单时说漏了名字，服务器能发现并重写，再不行换成一句写死的点单，这样点单不会白送答案。

### 花费和限额

81. 作为用户，我想光顾跟文字回合一样用对话模型，我在设置里带了自带 LLM 的就用我自己的，思考强度跟我设的文字回合那一项，这样不用另配。
82. 作为用户，我想光顾有自己的每小时次数（默认 5 次），不占文字回合和通话的次数，这样玩酒吧不耽误和她说话。
83. 作为用户，我想用自带 LLM 的光顾不计入限额，这样用自己的钱可以多玩。
84. 作为用户，我想进门时就算一次，重试不再算；第一次调用彻底失败、一句没写出来的退回给我；我自己中途离开的照常算，这样和文字回合一致。
85. 作为用户，我想超了限额时知道什么时候能再来，这样不用一直试。
86. 作为管理者，我想在后台的限额卡里设「光顾 / 小时」，在某位用户的页面上给他单独设（数字、不限或 0），这样和别的限额一样管。

88. 作为管理者，我想后台「限额与玩法」里有一张「酒吧」卡能开关，后台改的优先于 `.env`，这样不用重启。

91. 作为管理者，我想每次光顾在运行记录里是一条「光顾」，合计这次几次调用的用量、服务和快慢，记是否用了自带 LLM 和结果是哪种，不记台词，这样花费和服务状态把酒吧算进去。
92. 作为部署者，我想看板这一小节从运行记录汇总好的格子里取，不新增写入，这样库的负担不变。

## Implementation Decisions

### 饮品目录（新的配置文件，和礼物目录并排）

- `characters/drinks.toml`，从调研分支 `research/bar-drinks` 的 `drinks.csv` 转过来，28 款，不收 Flaming Moai。每款：
  - `id`：好认的写法（`sugar-rush`、`bad-touch`），不用原版缩写；
  - `name`：英文原名（配方书、备忘、中文字幕都用它）；`name_ja`：日文版译名（她的日语台词用）；`short_name`：原版的短名（份数槽里写的）；
  - 配方：`adelhyde`、`bronson_extract`、`powdered_delta`、`flanergide` 各几份，`karmotrine` 是份数或 `"optional"`；`ice`、`aged`；`method` 是 `mix`、`blend` 或 `bottle`；`big` 表示本身就是大杯、没有翻倍版（原本超过 10 份的 5 款）；
  - `flavor`（`sweet`、`bitter`、`sour`、`spicy`、`bubbly`）、`kind`（`girly`、`manly`、`classic`、`classy`、`promo`）；
  - `page`：配方卡的编号（前端找 `recipe_<page>.png`），瓶装没有；`description`：官方中文描述（配方卡上的，瓶装是小字），打比方的点单要用；
  - 瓶装另有 `karmotrine`：酒精份数（Absinthe 6、Rum 6、A Fedora 3、Mulan Tea 0）。
- 数据冲突照票 01 的建议：以配方卡为准（Piano Man 是 Sour），中文标签用菜单分类名（Classic 经典、Classy 时尚）。
- 启动时校验：id 唯一且合法；份数是 0 到 20 的整数、合计不超过 20；调制的不带瓶装份数，瓶装不带配方；口味、种类、调法在列表里；有配方卡的有 `page` 和 `description`；任意两款的配方不重合（包括大杯翻倍以后、可选 Karmotrine 展开以后），否则匹配会有歧义。坏了后端起不来（照 `JobListError` 的写法）。
- 后台不能改，也不交给后台模型生成。

### 配方匹配（饮品目录模块里的一个函数）

- 输入是上酒时调酒台上的样子：五种材料各几份、冰、陈化、调法（`mix` 或 `blend`）；或者一款瓶装的 id。输出是一款饮品加「大杯没有」，或者「调坏了」。
- 规则：份数（可选 Karmotrine 的那一项不比）、冰、陈化、调法和某款的配方完全一致就是那一款；份数全部是配方的两倍（可选 Karmotrine 照样不比）、其余一致就是那一款的大杯；本身就是大杯的没有翻倍版。都对不上是调坏的。照 Flaming Moai 的配方调出来对不上目录里任何一款，所以也是调坏的。
- **含不含酒**：瓶装看它的份数（Mulan Tea 是 0）；调制的看这一杯实际加了几份 Karmotrine。**这一杯的酒精份数**就是实际加的 Karmotrine 份数（大杯自然是翻倍后的），瓶装是目录里的份数。
- 前端（第二份规格）用 `GET /api/bar` 拿到的同一份目录即时显示短名和调坏的；上酒时把调酒台的样子原样交给服务器，由服务器重新匹配、判定、算醉。判定只认服务器的。

### 角色的口味（`characters.toml` 每人五列）

- 和 `liked_gifts` 放在一起：

  | 字段 | 内容 | 必填 |
  |---|---|---|
  | `bar_flavors` | 喜欢的口味，1–2 种 | 是 |
  | `bar_kind` | 喜欢的种类，0–1 种 | 否 |
  | `bar_favorites` | 爱喝的饮品，1–3 款，饮品 id | 是 |
  | `bar_disliked_flavor` | 讨厌的口味，0–1 种；推不出来就不填 | 否 |
  | `bar_tolerance` | 酒量：`weak`、`medium`、`strong` | 是 |

- 校验：口味、种类、酒量在列表里；爱喝的都在饮品目录里（两份都加载完以后查，照 `gift_catalog.check_liked_gifts`）；讨厌的口味不在喜欢的口味里，爱喝的饮品没有讨厌的口味。坏了后端起不来。
- 依据写进 `characters/facts/<id>.sources.md` 新的一节「酒吧口味」，每一条一句理由：剧情里有饮食偏好的引剧情，找不到的从人设推，标「人设推断」。酒量按年龄和性格推。爱喝的饮品尽量分散，不让一半人都爱同一款。
- 由一张起草票让 agent 读人设、角色资料和出处文件写出整张表，做完停下等用户校对。
- 写戏的模型拿得到她的口味、爱喝的、讨厌的口味和酒量，她可以在台词里自己说出来；任何接口都不返回这些。

### 来意和话题（`characters/bar_visits.toml`）

- 两张通用清单，照 `jobs.toml` 的做法：手写、启动时校验、写错了后端起不来、后台不能改、不让后台模型生成。
  - **来意**约 30 条：`id`、一句说明（给模型的）、基调（`happy` 开心、`annoyed` 烦躁、`tired` 疲惫、`down` 低落、`calm` 平静）。
  - **话题**约 12 条：`id`、一句说明。
  - 每条可选 `not_for = ["hazuki"]`（少数几条はづき不用，比如组合伙伴）。
- 校验：id 唯一合法、基调在列表里、`not_for` 里的角色存在、说明是单行，并且每位角色至少有若干条能用（不少于去重要避开的 3 条加 1）。
- 由一张起草票让 agent 写初稿，做完停下等用户校对。

### 写死的句子（`characters/bar_lines.toml`）

- 一份配置放所有不交模型写的句子，启动时校验：
  - **「请慢用」**：制作人每上一杯说的几句（中文）。
  - **点单的模板句**：名字检查两次都不过时顶上，按说法分（直说名字、名字加大杯的带 `{name_ja}`、`{name}` 占位，其余不带名字），每条日语加中文。
  - **兜底的反应**：告别那次调用写不出来时用，按三档分（上得最好、上对、上错），每档几句，日语加中文。
  - **兜底的告别**：同上，按醉没醉分两组。
- 由一张起草票让 agent 起草（只写中文和日语各一份），做完停下等用户校对。
- 点单备忘不在这里：它是服务器按点单卡套的固定格式（见「点单备忘」），写在代码里。

### 一次光顾的状态（新的深模块，后端内存里）

- **酒吧模块**对外只有几个动作：读（开关、目录、今天还有没有奖励）、进门、上一杯、再试一次、离开。它自己管抽取、判定、醉、提示词、调用、解析、名字检查、写结果和发奖励；接口层只做 HTTP 和 SSE。
- 每位用户同时最多一次光顾，放在内存里（照通话的做法），每次光顾一个随机的 `visit_id`。状态里有：角色、进门的时刻和北京日期、来意、话题、计划的杯数、已经写好的每段台词（给下一次调用的提示词用）、每一单的点单卡、每杯上了什么和判定、累计的酒精份数、醉没醉、现在停在哪一步（正在写、等上酒、出错停住、已告别）、最后一次动作的时刻。
- 新开一次光顾时，这位用户已有的那次作废（运行记录照「离开」结束）。最后一次动作过了 `IDLE`（30 分钟）的光顾作废，下一次碰到它或者后台定期扫时结束。后端重启时进行中的光顾直接没了，运行记录也不写，接受。
- 跨零点：一次光顾按进门那天（北京日期）算，「当天第一次」「当天的角色」都看进门那天。

### 选角色、来意、话题、杯数（进门时抽）

- **角色**：这位用户在今天（北京日期）还没有玩完的光顾时，是**今天的角色**：用用户 id 加日期做种子的确定性散列，在全部角色（`characters.toml` 的顺序，含はづき）里取一位，所以同一天怎么重进都是她，换一天换人；以后加了角色，结果跟着变，无所谓。今天已经玩完过的，从全部角色里随机一位，各位同等可能。冷却中、好感度低的她都不剔掉。
- **来意**：这位用户今天给她排的、已经做完的那项工作（`schedule` 模块读她今天的放置；日程关着或没有就没有）存在时，一半概率拿它当来意，带那项工作的名字和说明。否则从清单里抽，避开这位用户和这位角色最近 3 次玩完的光顾用过的来意（`not_for` 也剔掉），抽空了就放开这条限制；日程当来意时不受这条限制。
- **话题**：同样的去重方法从话题清单里抽。
- **杯数**：1 杯 20%、2 杯 60%、3 杯 20%。
- 数都来自后端建造时给的随机源（`randomness.Random`），测试换成 `FakeRandom`。

### 点单怎么抽（每次要写点单的那次调用之前抽，存进状态，重试时不重抽）

- **目标饮品**：先抽桶，再在桶里同等可能地抽一款：
  - 爱喝的 45%：`bar_favorites`；
  - 合口味的 35%：口味在 `bar_flavors` 里或种类等于 `bar_kind`、又不在爱喝的里面的；
  - 心血来潮 20%：任一款。
  - 所有桶都剔掉：讨厌的口味；这次光顾已经点过的；这是第一单时，她上一次玩完的光顾点过的（「点过的」见「老样子」）。某个桶剔空了就落到下一个桶，心血来潮也剔空了就不剔「上次点过的」再抽一次。
- **说法**：在这一单能出的说法里按占比抽（不能出的去掉、其余按比例摊）：

  | 说法 | 占比 | 能出的条件 | 算对的范围 | 上得最好 |
  |---|---|---|---|---|
  | 直说饮品名 | 40% | 都能出 | 只认目标这一款 | 没有这一档 |
  | 饮品名加大杯 | 7% | 目标有大杯 | 目标这一款，小杯也算对 | 目标的大杯 |
  | 说口味 | 12% | | 目标这个口味的都算 | 范围里她爱喝的 |
  | 说种类（可以绕着说） | 12% | | 目标这个种类的都算 | 同上 |
  | 几个条件叠加 | 8% | 不是新手；目标至少有一个附加条件可出 | 条件全满足才算 | 同上 |
  | 照描述打比方 | 8% | 不是新手；目标有 `description` | 只认目标这一款 | 没有这一档 |
  | 「来杯我喜欢的」 | 4% | 目标从爱喝的桶里抽出；她和这位用户至少玩完过一次光顾 | 她爱喝的，或口味、种类合她心意的 | 她爱喝的 |
  | 「你拿主意」 | 4% | | 都算 | 她爱喝的 |
  | 「老样子」 | 5% | 她和这位用户至少玩完过一次光顾 | 上次光顾她点过的任一款 | 没有这一档 |

- **几个条件叠加**：从目标的口味或种类里取一样，再从目标能出的附加条件里取一到两样：加冰（目标加冰）、无酒精（目标能选 Karmotrine 或本身无酒精）、大杯（目标有大杯）。说了大杯就要大杯，说了加冰就要加冰的饮品。
- **通用规则**：她讨厌的口味在任何说法下都算上错。她没提到的条件不管。范围里没有她爱喝的，这一单就没有「上得最好」这一档。
- **酒量补一句「不要酒精」**：目标能选 Karmotrine（那 7 款）、说法不是「老样子」时，酒量弱的 40%、中等的 10% 补一句，强的不补；补了就加上无酒精条件，照硬条件判（上了含酒的算上错）。
- **新手**：这位用户玩完的光顾（任何角色）不到 3 次。门槛是常量。
- **「老样子」的「上次点过的」**：她和这位用户上一次玩完的光顾里，每一单「她要的那款」：那一单上对或上得最好时是当时上的那款，上错时是那一单的目标饮品。备忘只写「她要上次那款」，不复述。不受「第一单避开上次点过的」限制。
- **点单卡**：交给模型的是说法、目标饮品的名字（英文和日文）、口味、种类、描述（打比方时）、这一单要提哪些条件（口味、种类、冰、大杯、不要酒精）、能不能说出名字。范围和「上得最好」不给模型。

### 点单备忘

- 每一单的备忘由服务器按点单卡套固定格式，用制作人的口吻：「她要 Sugar Rush。」「她要 Sugar Rush，大杯。」「她要甜的。」「她要时尚的。」（种类用菜单分类名：女性化、男性化、经典、时尚、宣传）「她要甜的，加冰，不要酒精。」「她要她喜欢的。」「她让你拿主意。」「她要上次那款。」；打比方的复述她点单那句的中文字幕（名字检查过了以后的那句）。
- 备忘随点单句一起推给前端，一直看得到，下一单开始时换掉。

### 判定（上一杯）

- 服务器先匹配：调坏的拒绝（422，什么都不变）；能上的判成三档之一：在「上得最好」里是上得最好，在范围里是上对，否则是上错。
- **上错时错在哪**，按这个顺序取第一条符合的：上了她讨厌的口味；说了不要酒精却有酒；「老样子」却不是上次那款；口味对了种类不对，或种类对了口味不对（和目标比）；完全不对。前两条交给模型时要求写成明显的不喜欢；好感度和别的上错一样。
- 上错不让重做，下一单照点，没有惩罚。
- **醉**：累计这一杯的酒精份数；累计到她酒量的门槛（`weak` 8、`medium` 14、`strong` 20，常量）就醉了。只分没醉和醉了；判定只看点单条件，往可选 Karmotrine 的饮品里多加酒仍然是那一款；醉了不加分也不减分。

### 提示词（酒吧自己的一套，ADR-0020 的排法）

- 不和文字回合共用前缀，不给工具（没有回忆工具），不检索记忆，不调判断模型。
1. **共用的系统块**（打缓存标记）：她的人设、她的生日那句、世界设定、IF 的设定和护栏（所有角色都已到能喝酒的年纪，她仍是 283 的偶像、制作人是她的制作人，下班后在 VA-283 当酒保；不提具体年龄、不讨论「其实没成年」，界面不解释 IF；醉了只是话多、犯困、情绪起伏、说心里话，不往暧昧和色情走，「不该说的话」照旧）、酒吧的写法（骨架每段写什么、几句，制作人每段最多一两句、只是接话，只写中文；不写选项；不替服务器决定对错）、输出格式。同一天她对所有用户都一样。
2. **这次光顾的块**：制作人的档案（和文字回合同一段）、来意（来自日程时带那项工作的名字和说明）和它的基调、话题、计划点几杯、好感度档位的那几句（`affinity_prompt`，关着时按正常值不写）、`today_lines`（她和别人的生日、日本节假日、往年今天的演出）、她在酒吧的记录（第一次来 / 来过几次 / 常客；上次是多久以前，很久没来要提；上次每单点了什么、档位；上次醉没醉）、她的口味（喜欢的口味和种类、爱喝的、讨厌的、酒量）。整次光顾不变。
3. **前面已经写好的**：每次调用「这次要写什么」是一条 user 消息，写出来的台词作为一条 assistant 消息，依次接上；末尾那条打缓存标记。
4. **这次要写什么**（最后一条 user 消息）：要写哪几段（进门加点单 / 反应、闲聊加下一单 / 反应、短闲聊加告别）、点单卡、这一杯上的是哪款（名字、口味、种类、大小、含不含酒）和判定、上错时错在哪、「从这一段起你醉了」、告别时每一杯的档位和醉没醉。
- 进门的写法按她来过几次分：第一次来、常客（玩完过 5 次及以上，常量）、很久没来（上次超过 14 天，常量）；当天是生日、节日的在进门时提一句。
- 每次调用的思考强度跟「对话模型 · 文字回合」那一项（自带 LLM 的用他们自己设的文字回合强度），不新开一项。缓存照 ADR-0020：Anthropic 显式打标记，其余靠服务商的自动前缀缓存。

### 输出格式和解析

- 沿用文字回合的标签写法（`reply_format.py`），一句一组：

  ```
  <her emotion="happy"><ja>…</ja><zh>…</zh></her>
  <her emotion="calm" order="true"><ja>…</ja><zh>…</zh></her>
  <producer>…</producer>
  ```

- 情绪是七种之一（calm、happy、shy、surprised、sad、angry、thinking），由写台词的模型标，不在七种里就当 calm；制作人的台词不标。不调判断模型。
- **点单句**：要点单的那次调用，她说出点单的那一两句标 `order="true"`，并且放在这次输出的最后。一句都没标的，把她的最后一句当点单句。
- 解析器照 `ReplyParser` 写一个酒吧用的，边收边解析，每收完一句交出一句。她的台词缺 `<zh>` 就拿日语那句当字幕；缺 `<ja>` 的那句丢掉；标签外的文字丢掉。一句完整的都解析不出来算格式不合格。
- 不用 JSON 模式（模型那一层没有，ADR-0019 也不维护按服务商的兼容表）。

### 名字检查

- 只看点单句。不该说名字的说法（直说名字、名字加大杯以外的全部）：日语和中文字幕里都不能出现目录里任何一款的英文名或日文名（不分大小写、全角半角）。该说名字的（直说名字、名字加大杯）：中文字幕里要有目标的英文名，或日语里要有它的日文名；名字加大杯还要提到大杯（检查交给提示词，不做字面检查）。
- 点单句先扣在服务器，不往前端推；这次调用写完后检查，过了再推出去，同时推备忘。
- 不过：用同样的提示词加一句「只重写点单那一两句，不要提任何饮品的名字 / 一定要说出名字」再调一次，只取点单句；还不过就换成 `bar_lines.toml` 里这种说法的模板句。重写那次不算重试，也不另计限额。打比方的模板句没法照描述打比方（描述里有别的饮品名，也只有中文），只说出目标的口味和种类，所以换成模板句的打比方，这一单改按「几个条件叠加」（目标的口味加种类）处理：算对的范围、「上得最好」、备忘（「她要甜的，时尚的。」）都照条件叠加，光顾记录里也记成条件叠加（2026-10-26 用户定，见票 04）。

### 接口（只给登录、同意了条款的用户）

- `GET /api/bar`：关着时只返回 `{"enabled": false}`。开着时返回：
  - `drinks`：饮品目录（id、英文名、短名、配方、冰、陈化、调法、是否本身大杯、口味、种类、配方卡编号、瓶装的描述和份数），前端调酒台和配方书用；不含只给模型的东西（日文名、配方卡的描述，配方卡上的字前端看图），也不含任何角色的口味。
  - `reward_today`：今天（北京日期）还没玩完过光顾，并且好感度和礼物开着（`LiveConfig.affinity_on`）。第二份规格的玩法页卡用。
- `POST /api/bar/visits`：进门，正文带自带密钥（和文字回合同样的 `own_keys`）。先过准入（见「限额和准入」），再抽角色、来意、话题、杯数、第一单，开始第一次调用。回答是 SSE（`text/event-stream`，照文字回合的写法）：
  - `visit`：`visit_id`、`character_id`；
  - `line`：一句台词，`speaker`（`her` 或 `producer`）、她的 `emotion`、`ja`、`zh`、点单句另带 `order: true`；
  - `memo`：这一单的备忘，跟在点单句后面；
  - `waiting`：这次调用写完了，等制作人上酒；
  - `retrying`：这次调用失败了、正在重试，前端把这次调用推来的句子清掉；
  - `failed`：重试后还是失败，带一句短的出错提示，停在这次调用之前；
  - `done`：告别写完了（见「玩完」），带 `rewarded`：`{"draws": 0 或 1, "affinity_up": true/false}`，什么都不给时是 `null`。
- `POST /api/bar/visits/{visit_id}/serves`：上一杯，正文是调酒台的样子（五种材料各几份、`ice`、`aged`、`method`）或一款瓶装的 id，加 `own_keys`。调坏的 422（`broken_drink`），不是等上酒的时候 409。能上的：先推一句服务器挑的「请慢用」（`line`，`speaker: producer`），再开始下一次调用，推法同上；最后一杯或醉了的那次以 `done` 收尾，否则以 `waiting` 收尾。
- `POST /api/bar/visits/{visit_id}/retry`：停在出错的那次调用上时再调一次（用存下的点单卡，不重抽），推法同上；不是出错停住的时候 409。
- `DELETE /api/bar/visits/{visit_id}`：离开，204。
- 不存在、已作废、已告别、不是这位用户的 `visit_id` 一律 410（`visit_gone`），前端回店门口。
- 关着时进门 409（`bar_closed`），已经在进行的光顾照常走完。部署者没有对话模型、用户也没带自带 LLM 时进门被拒，和文字回合同一种回答。
- 一次调用还没写完时 SSE 断开（页面没了、断网），这次调用停下，照「离开」结束这次光顾；告别那次在写完之前断开也一样，不算玩完。推完 `waiting` 或 `failed` 后流正常关闭，光顾留着等下一个动作。
- 前端只靠这些事件显示，不从别处知道判定：判定不推给前端（界面不显示档位），醉意也不推。

### 出错和重试

- 每次调用（超时、模型报错、格式不合格）自动重试 1 次（文字回合不重试，这里单独加），推 `retrying`。还不行推 `failed`，状态停在这次调用之前，等「再试一次」或离开。
- **告别那次调用**（反应加告别在同一次）重试后仍写不出来：反应用 `bar_lines.toml` 里这一杯档位的兜底句，告别用醉没醉那一组，**照样算玩完**，奖励照发。
- 名字检查不过的处理见上，不算出错。
- 「再试一次」不另计限额。

### 玩完、光顾记录和奖励

- **玩完**：告别那次调用写完（或用兜底句顶上）的那一刻。在同一个写事务里：写光顾记录、发奖励；然后推 `done`。在那之前离开、断开都不算。
- **光顾记录表**（用户数据）：一次玩完的光顾一行：用户 id、角色 id、进门和告别的时刻、进门那天的北京日期、来意 id（来自日程时记工作的名字）、话题 id、每一单（目标饮品、说法、上的饮品、大杯没有、档位）、醉没醉、这次有没有发奖励。不存台词。一直留着；「来过几次」数行数，去重取最近 3 行，「老样子」和「上次」取最近 1 行，「当天第一次」查这位用户这一天有没有行，「新手」数这位用户的行数。
- **奖励**（只有这一天还没有别的玩完的行、并且好感度和礼物开着时）：
  - **抽奖**：给 1 次，和每天发的一样受上限 7（`affinity.MAX_DRAWS`）约束，攒满了就不给。先照常补上今天该发的（`gifts._give`），再加；加上了才记一笔到账（`gift_rewards` 一行，键按日期，如 `bar:2026-10-26`），所以导航「玩法」上的点照旧亮；没加上就不记。成就的到账不受上限，这一条受，所以要一条受上限的新路径，不能直接用 `Gifts.reward`。
  - **好感度**：每杯上得最好 0.5、上对 0.4、上错 0.1；没有「上得最好」这一档的单（直说饮品名、打比方、老样子，或范围里没有她爱喝的）上对记 0.5；取这次每一杯的平均，最多 +0.5。走做完工作那条路（`Affinities._raise` 的通用化）：冷却中也加（加的是这个数，不是冷却中礼物的固定 +3）、到解冻线解除冷却、不受每天上限约束、不留对话事件、不出胶囊。常量和别的好感度数值放在同一个模块里。
  - `done` 的 `rewarded`：给了抽奖 `draws` 是 1，攒满了是 0；好感度加了 `affinity_up` 是 true。关着、或今天已经玩完过时是 `null`。
- 光顾不写对话记录、不写记忆、不留对话事件，不进统计页、成就、分享图。

### 限额和准入

- `usage` 加一种 `visit`，`user_limits` 加一列 `visits_per_hour`（照 `photos_per_hour` 的加列写法）；环境变量 `EIDOLON_VISITS_PER_HOUR`，默认 5；实时配置的限额项加一项「每小时光顾次数」；管理者的用户页单独设的限额多这一项（数字、不限、0）。`OverLimit` 的名字表加「光顾」。
- 准入照 `Admissions` 的做法加一种 `visit`：拿钥匙（自带的照文字回合 `for_turn`）、开运行记录、再占一次限额；超了记「被拒」并回 429，带什么时候能再来。**不检查冷却**（冷却中的她照样会来）。
- 计数：进门那次占一次，重试、「再试一次」、重写点单不再占。第一次调用彻底失败、一句没写出来就结束的退回；其余（玩完、中途离开、后面的调用出错）照常计。用了自带 LLM 的不计数，只记下来（`exempt`）。

### 运行记录和看板

- `RecordKind` 加 `visit`：一次光顾一条，结束时写（玩完、中途离开、超时作废、被新光顾顶掉、出错放弃都算结束）；这次 2–4 次调用（加重写点单）的服务调用都挂在它下面，所以用量、花费和服务状态跟着它走。结果：玩完 `success`；最后停在一次彻底失败的调用上就结束的 `failed`；被拒的 `rejected`；其余 `left`。记 `own_keys`（用了自带 LLM 没有）、`character_id`；不记台词，不记判定。
- `TURNS_AND_CALLS` 不含它；管理者用户页的「用了多少」照现在只数回合和通话。
- 看板「用量」加一小节「酒吧」（照「搭话」那一节）：这段时间里光顾了几次（不算被拒的）、玩完几次、失败几次，从运行记录汇总好的格子里取，不新增写入；酒吧开着或这段时间里有过光顾时才给，否则是 null。不加现查的「今天光顾过的人数」一类。

### 开关和后台

- `.env` 加 `EIDOLON_BAR`：不填或 `1` 开，`0` 关，其他值启动报错（同 `EIDOLON_SCHEDULE` 的 `_switch`）。实时配置加一项 `bar`（字段 `enabled`），暴露 `bar_on`；后台配置页「限额与玩法」标签加一张「酒吧」卡（只有开关，照「日程」卡，不「试」），后台改的优先（ADR-0013）。
- 关着时：`GET /api/bar` 返回没开；进门 409；进行中的照常走完。好感度和礼物关着时照样能玩、什么都不给。
- 酒吧依赖对话模型，不依赖判断模型。

### 数据和删除

- 光顾记录表登记进 `USER_DATA`（删账号、删除全部数据一起删）；删一段对话不碰它。不做清理，行数很小。
- 不进数据包，格式保持 3；`docs/data-package-format.md` 导入时「不在数据包里」那一句和 README 数据包那条补上光顾记录（ADR-0025 不用改，它是「只能在这个部署里挣来」那一类）。
- 部署前手动备份（新表、`user_limits` 加列）。

### 开发用的终端脚本

- 一个只给维护者用的脚本（不进 `eidolon` 命令），载入根目录 `.env`，用部署者的对话模型直接驱动酒吧模块走完整一次光顾：可以指定角色、每单的说法、每杯上成哪一档（脚本替制作人挑一款符合的），也可以让它醉；打印每句台词（说话人、情绪、日语、中文）、备忘、名字检查重写了几次、每次调用的用量和用时。不写库（用临时库），不发奖励。
- 合并前用它跑一遍：每种说法、每种档位、醉、告别至少过一次，用户看过措辞再合（见「人工验收」）。

### 对外文档（这一份的收尾块）

- **隐私政策**：「我们保存哪些数据」加一条「酒吧」：每次玩完的光顾存了角色、时间、来意、话题、每单的饮品和档位、醉没醉，不存台词；进备份；不进数据包；删除全部数据时一起删除。改「最后更新」日期。曲目选择那半句归第二份。
- **使用条款**：不改。
- **`docs/configuration.md`** 三语：新一节「酒吧」：是什么（一句）、开关 `EIDOLON_BAR` 和后台卡、「光顾」限额和 `EIDOLON_VISITS_PER_HOUR`、走对话模型、自带 LLM 的不计数、好感度和礼物关着时什么都不给；目录、开关表、限额表、后台表格（看板加「酒吧」、配置加「酒吧」卡、限额加「光顾」）各加一行。
- `docs/data-package-format.md` 和 README 数据包那条补一句（见上）。README 的功能列表、截图和致谢归第二份。
- 中文先写，用 humanizer-zh 过一遍再删减；英文、日文照中文定稿翻。

## Testing Decisions

- 只测对外的行为：接口给了什么、拒绝了什么、推了哪些事件、提示词里有没有那几样东西、库里留没留下什么、好感度和抽奖次数变成多少、看板上的数；不测抽取内部怎么摊比例，不测解析器的内部状态。
- **接缝一：后端 HTTP 接口**（`make_client` 加 `FakeClock`、`FakeRandom`、`FakeLLM`、`FakeServiceClients`，判断模型照 `test_gift_draws.py` 的写法打开好感度；读 SSE 照 `test_text_turn.py`；从 `llm.prompts` 看提示词；库里的东西照现有做法用 sqlite 直接查）。`FakeLLM` 照脚本吐 `<her>`、`<producer>` 标签，`FakeRandom` 控制角色、来意、话题、杯数、目标饮品和说法：
  - **走一次**：进门推 `visit`、几句 `line`、点单句、`memo`、`waiting`；上一杯先推「请慢用」再推反应；最后一杯推 `done`；调用次数是杯数 + 1；提示词里每次都有共用块、光顾块、前面写好的台词和这次要写什么，两处缓存标记在对的位置；不给工具。
  - **选角色**：同一用户同一天反复进门都是同一位（中途离开再进也是）；换一天换人；玩完后再进是随机的；冷却中的她照样能来、不被拒；跨零点进门那天算。
  - **来意和话题**：最近 3 次用过的不再出现，抽空了放开；今天做完的工作一半概率当来意、提示词里有它的名字和说明；日程关着时没有；`not_for` 的不给はづき。
  - **点单**：讨厌的口味永远不是目标；同一次不重复；第一单避开上次点过的；每种说法的能出条件（新手不出打比方和条件叠加、没玩完过的不出「老样子」和「来杯我喜欢的」、没大杯的不出名字加大杯）；酒量弱的补「不要酒精」；点单卡给模型的东西不含范围；备忘每种说法的文字。
  - **判定**：每种说法下上得最好、上对、上错各一例，以及边界：没说大杯做了大杯、名字加大杯上小杯、说了无酒精上了含酒的、讨厌的口味在宽说法下、「老样子」认上次那几款、范围里没有爱喝的；错在哪的每一种和优先顺序；调坏的 422 且状态不变；瓶装能上。
  - **醉**：三档门槛、大杯翻倍的份数、瓶装份数（Mulan Tea 0）；醉的那次调用要求写反应、短闲聊和告别，后面的单不再点；提示词里有「从这一段起你醉了」；记录记醉了。
  - **名字检查**：该说没说、不该说说了（英文名、日文名、大小写、全角半角）各触发一次重写；重写还不过换模板句；点单句在检查前不推出去；备忘用的是过了检查的那句。
  - **出错**：一次超时自动重试、推 `retrying`；两次失败推 `failed`、状态停住，「再试一次」接着走且不重抽点单；格式不合格同样处理；告别那次两次失败用兜底句、照样 `done` 并发奖励；`retry` 不在出错停住时 409。
  - **状态**：另开一次光顾后旧的 410；30 分钟不动后 410；离开后 410；SSE 断开等于离开；不是这位用户的 410；上酒不在等上酒时 409。
  - **奖励**：当天第一次玩完抽奖 +1、好感度按平均上升（全上得最好 +0.5、全上错 +0.1、没有最好档的单上对记 0.5）；攒满 7 次时不给、不记到账；冷却中加这个数并在解冻线解除；第二次玩完什么都不给；中途离开什么都不给；好感度和礼物关着时 `rewarded` 为 null、库里没变；导航的「新到账」时刻跟着酒吧的到账走；不留对话事件。先例：`test_schedule_job_done.py`、`test_gift_draws.py`、`test_affinity_cooldown.py`、`test_reset_card_grants.py`。
  - **她记得上次**：第二次光顾的提示词里有来过几次、上次多久以前、上次每单的饮品和档位、醉没醉；常客和很久没来的门槛；中途离开的光顾不算进去；对话的提示词里没有任何酒吧的东西（先例 `test_dynamic_context.py`）。
  - **限额**：第 6 次进门 429 并带时刻；重试不占；第一次调用彻底失败就离开的退回；中途离开的照算；自带 LLM 的不计数但记下；管理者单独设的生效（数字、不限、0）；不占文字回合和通话。先例：`test_rate_limit.py`、`test_exempting_keys.py`、`test_admin_users.py`。
  - **自带 LLM 和思考强度**：带了自带 LLM 的用它的钥匙；思考强度跟文字回合那一项。先例：`test_own_llm.py`、`test_llm_effort.py`。
  - **运行记录和看板**：每种结束各一条、结果对、服务调用挂在下面、`own_keys` 对；看板「酒吧」的三个数、关着又没有记录时为 null。先例：`test_reach_outs_dashboard.py`、`test_activity_records.py`、`test_activity_rollups.py`。
  - **开关**：`EIDOLON_BAR` 不填为开、`0` 为关、其他值报错；后台配置改了优先；关着时读返回没开、进门 409。先例：`test_schedule_switch.py`、`test_live_config.py`。
  - **数据**：光顾记录表登记了（`test_database.py`）；删账号后不剩这位用户的行；数据包导出里没有、导入不动它（`test_data_package.py`）。
- **接缝二：配置模块**（照 `test_job_list.py`、`test_gift_catalog.py`、`test_characters.py`）：
  - 真实的 `drinks.toml`、`bar_visits.toml`、`bar_lines.toml` 和 `characters.toml` 的酒吧五列通过校验；临时配置里缺字段、重复 id、份数超 20、两款配方重合（含翻倍后）、口味拼错、爱喝的不在目录里、讨厌的口味和喜欢的重合、清单不够某位角色去重各被拒。
  - **配方匹配**：28 款每款的配方都匹配到自己；每款的大杯；本身就大的没有翻倍版；可选 Karmotrine 加 0 份、加几份都是那一款，含不含酒和酒精份数对；冰、陈化、调法差一样就对不上；Flaming Moai 的配方是调坏的；瓶装。
- 开发用的终端脚本不写测试。
